# Flight Recorder

A local desktop app for practising job interviews on webcam. Built with Electron. Runs fully on the user's machine — video, notes and speech-to-text alike. Nothing about a recording is ever uploaded, on any platform.

## Stack
- Electron on every platform (Linux, Windows, macOS): the same bundled Chromium everywhere, so capture and playback behave identically and nothing depends on the user's distro. The app moved off Tauri in v2.0.0 because on Linux Tauri has to use WebKitGTK, which couldn't record audio and video together, froze the camera's first frame for ~9s, couldn't play video from its own asset protocol, and needed the right GStreamer/H.264 packages on each machine. Linux is the main platform.
- Frontend is plain HTML/CSS/JS. No React or Vue, no bundler - ES modules served over `app://` (`electron/protocols.js`).
- `src/js/platform.js` is the only file in the UI that talks to the main process; everything goes through `window.flightRecorder` (`electron/preload.cjs`) to channels in `electron/ipc.js`. Keep it that way - the rest of the UI stays shell-agnostic.
- The main process (`electron/`) is deliberately small: `library.js` (every file operation, `realpath`-checked to stay inside `Videos/flight-recorder`), `protocols.js`, `security.js`, `window-state.js`, `whisper.js`, `updater.js`.
- `library.json` is a plain JSON file read and written whole (`Store` in `platform.js`, saved atomically by `library.js`) - not browser storage.
- Speech-to-text is a separate Rust program, `native/` (`fr-whisper`), run once per recording - see Speech pace below.
- Confirmation prompts (delete question/attempt) are an in-app modal, not the native OS dialog — keeps the UI visually consistent with the rest of the app.

## Core features
- Question bank, organised by category (Behavioural, Technical, Case). User can add and remove questions. Questions reorder by dragging, built on pointer events (`watchForDrag` in `questions.js`), not HTML5 drag-and-drop: that showed a translucent ghost copy, only registered a drop made on top of another question (not in the empty space below the list), and moved nothing until the drop. Now the question follows the pointer, the others slide aside, and a drop anywhere lands where the gap is. Nothing in the app accepts dropped files; a file dropped on the window would otherwise navigate to it, which `security.js` blocks along with every other navigation. (Under Tauri this needed `"dragDropEnabled": false`, whose default silently disabled DOM drag-and-drop in packaged Windows builds - worth knowing if reordering ever stops working in one build and not another.)
- Live webcam viewfinder using `getUserMedia`. Record/stop tied to the selected question.
- Each recording becomes a logged attempt. Captures question, category, date, and duration automatically.
- User adds a star score and notes after reviewing.
- Filter tabs over the attempt log (All / Behavioural / Technical / Case).
- Response delay: measures time from record start to first speech. Uses mic volume. Fully local. Works in any browser/webview. The threshold is *adaptive* — it tracks the room's noise floor (`trackNoiseFloor`) and requires speech to sit `SPEECH_NOISE_MULTIPLIER`× above it, rather than comparing against one hardcoded number. Raw mic levels differ enough between a headset and a laptop array that a fixed threshold was never fully reliable, even with auto gain control on (see below).
- Pace spread (`pace 110-175 wpm`): speaking rate per stretch of speech between real pauses (`computePaceRange` in util.js), showing variation the single average WPM hides — rushing the end of an answer is a real habit and otherwise invisible. Stretches come from the mic (`speechStretches`: `speechIntervals` joined across gaps under 1200ms, the same pause definition as `pauseCount`); each stretch gets the words said in it (see the drift rules under Transcript pauses) and long stretches are split into ~10s windows. It used to rate Whisper's own segments, which often contain a pause or the thinking time before the first word: the same known answer, spoken at a steady 156-173 wpm, came back 50-147, 90-116 and 72-120 on three runs. Windows under 2s are excluded, a single rate renders nothing rather than a fake "range", and without a mic measurement nothing is shown rather than the old, wrong figure.
- Whisper invents fluent-sounding sentences over silence. This is a well-known failure mode and it lands straight in the word count, dragging WPM with it. Its own no-speech probability is **not exposed by whisper-rs 0.14** (and `set_no_speech_thold` is documented there as unimplemented), so `rejectHallucinatedSegments()` cross-checks segment times against the intervals where the mic actually registered speech — an independent physical signal. Deliberately generous: any overlap keeps the segment, because dropping real words would be far worse than keeping an invented one. The intervals are passed through `saveAttempt` and thrown away, never stored — hundreds of entries per attempt, and `library.json` is read and rewritten whole.
- Speech analysis in review: pause count, longest pause, longest unbroken run, and talking ratio. All derived from the same mic-level loop as response delay, *not* from a transcript — so it works identically on every platform, including Windows, and needs no speech recognition turned on. Pauses only count after the first word (the gap before it is the response delay, measured separately) and need `PAUSE_MIN_MS` of quiet; `SILENCE_HOLD_MS` of hysteresis stops the dips between syllables registering as pauses.
- Filler-word count: shown only when a transcript exists. Best-effort by nature — Whisper keeps fillers far better than a browser speech API did, but still inconsistently, since it transcribes for readability rather than stenographic accuracy. A zero means "none survived transcription", not "none said". The pause figures are the trustworthy signal; treat fillers as a bonus and don't build anything load-bearing on them.
- Transcript pauses: a real gap between two consecutive words is shown as "…". Word boundaries come from whisper's own per-token timestamps (`params.set_token_timestamps(true)` in `run_transcription`; reconstructed by merging sub-word BPE tokens on a leading space) — but *where a pause happened* comes from the live mic-level detector's `speechIntervals` (`recorder.js`), not from whisper's own word-to-word gap. That was the first design and it was wrong: tested directly against two real recordings, including one with a pause the live detector measured at 37 seconds, and whisper reported the words either side of it touching with a 0ms gap. Its plain per-token timestamps don't preserve real silence duration once a gap runs past roughly a second — they just pack tokens back-to-back regardless — so a threshold on whisper's own gap (the original approach, `WORD_GAP_PAUSE_MS`) fired on nothing in real use. `joinWordsWithPauses` (util.js) finds real pauses from `speechIntervals` and uses whisper's word timestamps only to find *which pair of words* a real pause falls between, never to decide whether one happened. Even that needs care, because whisper's timing drifts around a silence in both directions: in a quiet room it stretched "while we switched" across a known 4s pause, with fan noise it pulled the next word back into it, and a real 37s pause had the words either side touching. What held up every time is where whisper starts a new segment - right at the pause. So `firstWordAfterPause` trusts, in order: a segment break inside the pause (the first word of each segment carries `segmentStartMs`, added in `transcribeAttemptInBackground`), then the first word timed where speech resumed, then the first word timed after the pause began. The pace spread uses the same rule to decide which stretch a word belongs to. Still deliberately not the experimental DTW alignment (`dtw_token_timestamps`): it wouldn't fix this (the problem is trusting whisper's timestamps for silence at all, not their precision) and still costs a per-model attention-head preset and a dedicated 128MB buffer. Words are built from a flat list across all *kept* segments, not per-segment text — this also surfaces the span of a segment `rejectHallucinatedSegments` drops, which otherwise vanishes with no sign it was ever there.

  The threshold for what counts as a large-enough pause is deliberately its own constant, `ELLIPSIS_PAUSE_MIN_MS` (3000), *not* `trackPauses`'s `PAUSE_MIN_MS` (1200) — a second real-recording lesson, after the first one above. Reusing 1200 seemed right (same signal, same meaning, one pause the review screen counts is one the transcript marks), but a real 166s recording a user flagged as full of ellipses on ordinary speech showed why it wasn't: simulating `trackPauses`'s exact algorithm tick-by-tick against that recording's real audio to get each pause's actual duration showed 18 of its 29 detected pauses sitting in a narrow 1200-1800ms band right above the threshold — ordinary breath and word-boundary dips barely crossing it, not real hesitation — with a second, greyer band up to about 2900ms. 3000ms clears both, and is also roughly where conversational-analysis research and interview coaching alike treat a silence as crossing from normal pacing into "they paused": at that bar the same recording drops from 33 marked pauses to about 3, the genuinely dramatic ones. `pauseCount` keeps using 1200 - it's an aggregate read as one number, where a slightly generous count costs little. An ellipsis is read one at a time, inline, where the same borderline detections read as constant hesitation instead.
- `echoCancellation`, `noiseSuppression` and `autoGainControl` are all hardcoded **`false`** in `acquireStream()` - not settings. Any one of them engages Chromium's WebRTC processing chain, which is tuned for telephony intelligibility rather than fidelity: high-pass filtering, room-tone gating, level normalisation. Recordings came out audibly thinner and flatter than the same mic captured by Windows' own Sound Recorder, which defeats the point of an app for reviewing your own delivery. The trade is deliberate: room tone, fan noise and breaths are audible now, because they always were and the processing was hiding them.
- **Microphone gain** (Settings, `micGainDb`, default +18; was +12 until measured on a real headset mic - speech still sat around -31 dBFS at +18 with peaks near -10 and no clipping) is a static makeup gain applied through a `GainNode` in `startWaveformMonitoring()`. It exists because AGC was what made the old recordings loud, and removing AGC removed the loudness with it. Unlike AGC this is one constant multiplier for the whole take, so it lifts the recording without flattening it. **The analyser is deliberately connected *after* the gain node**: `SPEECH_RMS_FLOOR` and `WAVEFORM_GAIN` were tuned against AGC-processed audio, and raw speech sits close enough to that floor that quieter passages would stop registering and take the pause counts and response delay with them. Reading the gained signal also means what's analysed is exactly what's recorded. `recordingAudioTracks()` falls back to the bare mic track if the Web Audio chain isn't up - quiet audio is an annoyance, no audio is a lost attempt.
- **`autoGainControl:false` is only safe because of `normaliseForTranscription()` in `util.js`.** AGC was previously forced on after real testing showed that without it, quiet mics recorded quietly enough that Whisper transcribed *nothing at all*, silently. That's now handled after the fact instead: the webview levels the copy of the audio Whisper receives (RMS-targeted, gain-capped so a near-silent recording can't have its noise floor amplified into hallucinated speech) while the saved recording keeps its real dynamics. **These two changes are coupled - if that normalisation is ever removed, `autoGainControl` has to come back on.** Don't unpick one without the other, and test a real quiet recording end to end when touching either: the failure mode is an empty transcript with no error.
- Speech pace (WPM): word-per-minute estimate plus a transcript, shown read-only during review when present. WPM is words over the span from the first word to the last as the mic heard them (`computeWpm`), not over the whole recording: that counted the thinking time before answering and the silence before Stop as slow speech (an answer spoken at 125 wpm read as 100, and more thinking time read as slower speaking). `attempt.wpmMeasuredOver` records which: `"speech"`, `"recording"` (no mic measurement), or `"recording-minus-delay"` for attempts from before the fix, corrected once on load by `correctLegacyWpm` using the response delay they stored (their mic timing wasn't kept, so that's the best available). One backend on every platform — a local Whisper model (`whisper-rs`/whisper.cpp), run after the recording stops by `fr-whisper` (`native/`), a separate program `electron/whisper.js` spawns once per recording: `fr-whisper transcribe --model <file> --pcm <file>`, which prints **exactly one line of JSON on stdout** (`{ok:true,...}` or `{ok:false,error}`) - whisper.cpp logs to stderr, and anything else on stdout breaks the contract. It's a separate process on purpose: it's the one part compiled for a CPU instruction set, and when that went wrong (the AVX-512 crash below) the whole window vanished; now a crash is a stored `transcriptError` ("uses a processor instruction this computer doesn't have") and the app stays open. It never touches the network - main downloads the model and passes its path. **The audio is decoded in the renderer, not in Rust** — `extractPcmForTranscription()` in `attempts.js` uses `decodeAudioData` on a 16kHz `OfflineAudioContext` (which resamples as it decodes) and writes raw f32 PCM next to the video for `fr-whisper` to read and delete. Rust used to demux and resample this itself with symphonia and rubato; that could never work, because Chromium's MP4 muxer omits the `esds` SLConfigDescriptor that symphonia's isomp4 reader treats as mandatory, so every WebView2 recording failed with `isomp4: missing sl config descriptor`, and WebM recordings failed separately since symphonia has no Opus decoder. It went unnoticed for months because a failed transcription used to render as "No speech detected in this recording". Don't move the decode back into Rust: the webview can always read a file it just wrote, and no Rust-side demuxer can promise that. The model (~60MB) downloads once, on first use, to the OS app-data directory (not the portable `Videos/flight-recorder` folder - it's app infrastructure, not user data), gated behind an explicit confirmation dialog before it fetches anything. That directory is still the Tauri builds' (`appDataDir()` in `electron/paths.js`: `~/.local/share/com.flightrecorder.app` on Linux, not Electron's `~/.config`), so existing downloads are reused. The download is checked against a pinned SHA-256 and size (`electron/whisper.js`) before it's renamed into place. **Whether it's present is read from the filesystem (`whisper:present`), never from a stored flag** - the settings live in `library.json` under Videos and the model lives in app-data, so the two can be deleted independently. A `whisperModelDownloaded` boolean in the store used to answer this, and after app-data was cleared it said "downloaded" about a file that was gone: the confirmation dialog was skipped and the next recording silently fetched 60MB. Transcription also refuses to download - only `whisper:download`, the channel behind the prompt, ever fetches. Windows used to use the browser's `SpeechRecognition` API instead, live during recording; that was dropped deliberately. It was the only thing in the app that sent audio off-device, it produced different WPM numbers from Whisper for identical speech (useless in an app about tracking progress), and it silently stripped filler words, which broke the filler count. Live updating was the only thing lost, and you're talking rather than reading a counter while it would have mattered. **Don't reintroduce a second backend** — the cost of two is exactly what this removed.

## Data rules
- Video files write straight to disk, in a folder structure like `videos/{category}/{date}_{question-slug}.mp4`. Recording is **MP4/H.264 on every platform, with AAC audio where the platform can encode it and Opus on Linux** - Linux Chromium has an H.264 encoder (OpenH264) but no AAC encoder, so every `mp4a.40.2` type is unsupported there. The in-app player is Chromium on every OS, so both play back everywhere in the app; the cost is that a Linux recording may not open in QuickTime outside it. `RECORDING_FORMAT_CANDIDATES` in `recorder.js` tries H.264 High → Main → Baseline with AAC, then the same with Opus, then generic MP4, and only falls back to WebM/VP9 on an engine with no H.264 encoder at all. The Opus entries must stay **before** the bare `video/mp4`: left to choose, Chromium puts VP9 in the MP4. The extension is still whatever `MediaRecorder` actually negotiated, so never assume one when reading a video path back.
- Recording is held to the quality preset, not to whatever the camera happens to hand back. `getUserMedia` constraints are `ideal`, so a webcam with no 480p mode returns 720p; `computeRecordingSize()` sizes the watermark canvas to the preset (capped by the source, never upscaling) and `drawCoverFrame()` centre-crops rather than stretching a non-16:9 camera. Sizing off the camera's native resolution instead would silently record more pixels than the chosen bitrate can carry.
- Bitrates assume a low-motion talking head in H.264 at 24fps (`WATERMARK_FPS`). Audio stays at 128k — for an app about reviewing your own speech and cadence, audio is the primary signal and isn't where to save space. Don't drop the frame rate below 24 either; gesture and delivery are what the video half is actually for.
- Metadata (questions, scores, notes, delay, WPM, transcript) saves to `library.json` (`store.js`, via `Store` in `platform.js`), deliberately placed *inside* `Videos/flight-recorder/` (next to the video files it describes) rather than the OS-hidden app-data directory. The whole `flight-recorder` folder is meant to be one portable, self-contained unit — copy it to a different machine (even a different OS) and it just works, no export/import step. This only holds if `attempt.videoRelativePath` stays relative to that folder (never store an absolute path there) - `resolveVideoPath()` in `attempts.js` is the only place that turns it back into a real path, resolved against wherever the *current* machine's Videos folder is. New paths are stored with `/` and read back split on either slash: libraries recorded on Windows before v2.0.0 stored `behavioural\\file.mp4`, which on Linux/macOS is one file name, so none of their videos opened after copying the folder over.
- Nothing is ever deleted automatically. Recordings accumulate indefinitely (roughly 39GB/year at daily 10-minute practice, at default 480p quality), which is a deliberate choice — the user wants old clips around to see how far they've come. Settings shows the folder's total size (`library:size`) so the number is at least visible. If auto-pruning is ever revisited, it must keep the first attempt at each question, since that's the actual benchmark being compared against.
- Bitrates in `QUALITY_PRESETS` are tuned for H.264, not VP9 - it needs roughly 25% more bits than VP9 for the same picture. Both presets got a +25% bump when recording switched to H.264 everywhere; forgetting this the next time either preset is touched will quietly under-deliver quality again, the same way it did the first time (real user testing caught it, nothing automated did).
- Nothing about a recording ever leaves the machine. Not video, not audio, not transcripts. The app touches the network in exactly two places: the one-off Whisper model download (opt-in, behind a confirmation dialog) and update checks. That's the whole list, and it's what the footer and About modal now claim unconditionally — so never add a third without flagging it first and changing that copy to match. It's enforced, not just true of today's code: `security.js` cancels every http/https/ws request from the renderer (both allowed uses run in the main process - the download through Node's `fetch`, updates through electron-updater's own session), spellcheck downloads are stopped on Windows/Linux because Chromium would otherwise fetch Hunspell dictionaries from Google - on **every** session (`stopSpellcheckDownloads()` hooks `session-created`), because switching spellcheck off wasn't enough and electron-updater's own session leaked the download too, in installed builds only. Two checks guard it: the end-to-end test fails if its netlog shows any request, and `scripts/check-network.js` runs the real packaged AppImage (CI and every release, before upload) and fails on anything but the update check.

## Design language
(Revised again — supersedes the card-based direction below.)
Dark, sleek, flat editor-style chrome. Near-black navy base. Panels are tightly packed with a small (6px) gap between them, each with its own complete hairline border — no shared/single-line dividers, no rounded corners, no drop shadows. A permanent left activity rail (icon strip) selects sidebar content. Blue/indigo as the primary accent (buttons, active tabs, selection, focus rings). Red for recording state and destructive actions. Gold for star ratings only. Segmented pill-style filter tabs are the one deliberately rounded/card-like control, kept as an accent against the otherwise flat chrome. Efficient, compact padding — not generous whitespace. Monospace for timers and numeric readouts. Sentence-case labels. Smooth transitions and soft glow effects on hover/active states rather than hard colour swaps.

Do not fabricate decorative metrics or visualizations for capabilities the app doesn't have (e.g. no fake "eye contact" or "clarity" score charts) — only real data (response delay, WPM, transcript, star score, notes) gets shown.

## Cross-platform packaging notes
- Camera/mic access uses standard `getUserMedia`/`MediaRecorder`. `security.js` grants only `media`, `clipboard-sanitized-write` (About → Copy) and `fullscreen` (the review player), and only to `app://`. With no handler Electron grants everything, so don't remove it.
- **Linux runs through XWayland (X11), not native Wayland.** Native Wayland in Electron can't do always-on-top, restore a window's position, or `setSize` (View → Reset view). The switch has to be on the command line: `app.commandLine.appendSwitch("ozone-platform", …)` is too late - the window is already created on Wayland and only the helper processes switch - and `app.commandLine.hasSwitch("ozone-platform")` is always true because Electron fills in its own; `relaunchIfNeeded()` in `electron/main.js` checks `process.argv` instead. The installed launchers pass `--ozone-platform=x11` (`linux.executableArgs` in `electron-builder.yml`); anything else gets one relaunch (~0.25s).
- **The same relaunch disables MangoHud.** A global `MANGOHUD=1` (a gaming overlay; the developer's own machine has it in `~/.bashrc`) injects a Vulkan layer into Chromium's GPU process, which crashes (SIGILL in `libMangoHud.so`) and silently drops the app to software rendering. `DISABLE_MANGOHUD` set from `main.js` is too late: the GPU process forks from a zygote made before JS runs. Check `coredumpctl info` for `libMangoHud` before blaming the app for a GPU or GTK crash on that machine - it also crashed Showtime, GNOME Camera, Brave and VS Code there.
- **Relaunch by spawning, never `app.relaunch()`.** Inside an AppImage, `app.relaunch()`'s helper runs from the AppImage's mount, which disappears when the process exits, so the app never came back. `relaunchIfNeeded()` spawns the new copy detached, which is safe only because it runs before the single-instance lock or any window exists.
- **Updates**: electron-updater, GitHub provider, `autoDownload`/`autoInstallOnAppQuit` off. On its own it trusts unsigned SHA-512s in `latest*.yml` and installs .deb/.rpm as root, so every release carries `update-manifest.json` (every platform's files and hashes, `scripts/update-manifest.js`) signed in CI with the key the Tauri updater used (`TAURI_SIGNING_PRIVATE_KEY`, via `tauri signer sign`); `electron/update-manifest.js` refuses any update not matching it. minisign's `ED` signatures hash with BLAKE2b-512, which Electron's BoringSSL doesn't have ("Digest method not supported" - plain Node's OpenSSL does, so unit tests alone won't catch it), hence `electron/blake2b.js`. For an AppImage, electron-updater starts the new version *before* the old one quits, so `updater.install()` destroys the window and releases the single-instance lock first - otherwise the new copy hits the lock and exits, leaving no app. Updates are disabled when running from source.
- **macOS**: needs macOS 13+ (Electron 44's floor). Ad-hoc signed only (`identity: "-"`, no Apple Developer ID), so users must use System Settings → Open Anyway, and Squirrel.Mac can't install updates in place - `install()` opens the release page there. Camera/mic usage strings are in `mac.extendInfo` (required, or `getUserMedia` fails outright). Still not verified end-to-end on real macOS hardware - do that before relying on a Mac build.
- **Windows**: `fr-whisper.exe` links the C runtime statically (`native/.cargo/config.toml`), or it fails on machines without the Visual C++ redistributable - which every CI runner has, so `release.yml` checks the imports with `llvm-readobj`. Not code-signed, so SmartScreen warns on first run.
- **VS Code's integrated terminal exports `ELECTRON_RUN_AS_NODE=1`** (it's an Electron app itself), which makes `electron .` run as plain Node and fail on line one. `npm start` goes through `scripts/start.js`, which clears it. Packaged builds have the `runAsNode` fuse off, so they're unaffected.
- **AppImage** uses the static runtime (`toolsets.appimage: "1.0.3"`), so it needs no libfuse2. Building .deb/.rpm locally on Fedora needs `libxcrypt-compat` (electron-builder's bundled Ruby wants `libcrypt.so.1`); CI's Ubuntu has it.
- Installer file names must not contain spaces (`artifactName` in `electron-builder.yml`): GitHub renames spaces in uploaded assets, and `latest.yml` would point the updater at a file that doesn't exist.
- Every platform needs CMake, a C++ toolchain, and libclang to build `fr-whisper` (bindgen needs libclang; locally `WHISPER_DONT_GENERATE_BINDINGS=1` uses whisper-rs-sys's bundled bindings instead, fine on x86_64 Linux). macOS needs `CMAKE_OSX_DEPLOYMENT_TARGET` (not `MACOSX_DEPLOYMENT_TARGET` — `whisper-rs-sys`'s build.rs only forwards `CMAKE_`-prefixed env vars), and Windows needs `LIBCLANG_PATH` set explicitly with a pinned LLVM, because bindgen doesn't find libclang on GitHub's runner image by itself and the image's LLVM version drifts between runs. `scripts/build-helper.js` builds and stages it per architecture into `native/dist/<arch>/` for electron-builder; the macOS release leg builds both architectures in one run so a single `latest-mac.yml` lists both.
- **whisper.cpp must never be built with `GGML_NATIVE` on.** It's ggml's default, and it compiles with `-march=native` — tuned to the *build machine's* CPU. GitHub's runners are AVX-512 Xeons, so every release up to v1.6.3 shipped AVX-512 (and AMX) instructions, and on any CPU without them (an i7-6700; AMD before Zen 4; consumer Intel from 12th gen on) transcription died with SIGILL in `ggml_vec_dot_f16`. It builds, passes every test and runs perfectly on the runner itself, which is why nothing caught it. `native/ggml-portable.cmake` forces it off, loaded via `CMAKE_PROJECT_INCLUDE_BEFORE` in `native/.cargo/config.toml`. It has to be that indirect: whisper-rs-sys 0.13 only forwards `WHISPER_*`/`CMAKE_*` env vars to CMake (a plain `GGML_NATIVE=OFF` is dropped), and whisper.cpp's `WHISPER_NATIVE` alias can only switch it *on*. If whisper-rs is ever upgraded to 0.16+ (whisper-rs-sys 0.15 forwards `GGML_*`), `GGML_NATIVE=OFF` can be set directly instead. The result is an AVX2+FMA+F16C baseline, which covers essentially every x86 PC since 2013. `.github/scripts/check-no-avx512.sh` disassembles the binary and fails if any ggml function touches a `zmm` register; CI and `release.yml` both run it on `fr-whisper` — keep both. Two things that make this fix easy to silently lose: **cargo must run from `native/`**, because it finds `.cargo/config.toml` by walking up from the *current directory*, not from `--manifest-path` (`build-helper.js` and the CI steps all do). And **cargo will not rebuild whisper.cpp when that config changes**: whisper-rs-sys's build script only re-runs when its `wrapper.h` changes, so an existing build keeps whatever flags it was first compiled with. Locally that means `cargo clean -p whisper-rs-sys`; in CI, bump the `rust-cache` keys in both workflows whenever whisper.cpp's CMake options change.
- **Help → Debug info** (`src/js/debuginfo.js`, `electron/diagnostics.js`) replaced the Developer tools menu item: a plain-text report of version, install type, OS, display (X11/Wayland), GPU acceleration, MangoHud, speech engine/model, camera and microphone (the real device behind "Default", via `pactl` on Linux), settings, library counts, the latest transcription error, and the recent log from both processes - including Chromium helper-process crashes, which are otherwise invisible. `src/js/diagnostics.js` must stay the **first** import in `main.js` with no imports of its own, or it misses errors from startup. It must never include transcripts, notes or question text, and the home folder is shown as `~`. Report an issue copies it automatically. Developer tools are still Ctrl+Shift+I (Cmd+Option+I), handled in `main.js` via `before-input-event`.
- Testing: `npm test` (unit tests, incl. the main process's path checks, protocols, speech helper handling and update signatures) and `npm run test:e2e` (Playwright drives the real UI with Chromium's fake camera and an espeak sentence as the mic; `FR_E2E_MODEL` adds transcription). `test/e2e/accuracy.e2e.js` records an answer with pauses at known places, at a real headset mic's levels, and checks every speech figure against the truth - run it after touching anything in the speech measurements (recorder.js's mic loop, util.js's WPM/pace/pause functions). It needs espeak-ng, ffmpeg and a model, so it runs in CI's Linux job and skips elsewhere. E2E tests run one at a time (`--test-concurrency=1`): the mic loop samples 30 times a second, and two apps recording at once compete for the CPU. The e2e test clears `MANGOHUD` and passes `--ozone-platform=x11`, or the app would relaunch itself out from under Playwright. `FLIGHT_RECORDER_VIDEOS_DIR` / `FLIGHT_RECORDER_DATA_DIR` point the app at a throwaway library and model folder - use them for any manual testing too, never the user's real library.
